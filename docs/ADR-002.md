# ADR-002 — Bounded workspace aggregates for the pilot

Status: implemented for local pilot, with explicit scale limits.

The original plan proposed normalized meal/expense/period tables. Migration 0001 preserves that initial schema. The implemented `/workspace` flow instead uses a **bounded per-mess JSON aggregate inside D1**, plus separate relational users, sessions, invitations, operation receipts, access index and append-only audit tables. This is an intentional architecture adjustment, not an additional mock/localStorage backend.

## Why

One conditional database UPDATE can atomically change the aggregate, write the operation receipt, write the audit delta and rebuild the membership access index through SQL triggers. Updating only `WHERE revision = expectedRevision` prevents lost updates and stale closes. A duplicate operation key aborts the statement, including its trigger side effects. Two concurrent requests against actual local D1 were tested: one succeeded and the stale one received 409.

All commands are validated by `src/domain/workspace.ts` on the server. Browser-side visibility never grants permission. Each read/write rechecks active membership from the current document. Authoritative session identity comes from the database, not from command payloads. Indexes accelerate membership discovery, invitation lookup, operation lookup and recent audit retrieval.

## Trade-offs / limits

- Whole-document writes grow with history. This is **not** the final large-scale storage architecture.
- Explicit pilot caps: 30 roster members, 2,000 expenses and 2,000 transfers per month, 24 periods, 100 tasks, 50 pending join requests and roughly 650,000 JSON characters per workspace. The size cap can be reached before the month-count cap. These are operational limits, not a paid tier.
- Five messes per account. Deploy only to a small controlled pilot first.
- Audit stores command data and before/after deltas, not a second full copy of the workspace on every action.
- Application-level audit immutability is not protection against a privileged database administrator.
- Domain limits are enforced in the API. Direct SQL access remains privileged operator access.
- Existing normalized foundation tables are not the active workspace ledger; do not read them as if they contain current workspace activity.
- Future migration: split the aggregate into indexed periods and posting tables, retaining versioned commands/receipts and exporting existing snapshots first. Benchmark Worker CPU and D1 write amplification before expanding.

No remote production throughput or Free-tier CPU-fit claim has been verified. This remains a release gate, especially at the upper bounds.
